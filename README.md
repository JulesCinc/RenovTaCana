### Comment lire les niveaux sur la grille (PDF)

Dans la grille, chaque critère est positionné sur une **échelle de satisfaction** (formulations du type *Absolutely*, *Somehow*, *Not really*, *Not at all*, etc.). En simplifiant :

- **Très favorable** (équivalent « vert ») : par ex. **Absolutely** — point fort explicite.  
- **Intermédiaire** (entre les deux) : par ex. **Somehow** — partiel, à consolider.  
- **Peu satisfaisant** (équivalent « rouge ») : **Not really** ou **Not at all** — à améliorer en priorité.

Les **commentaires manuscrits** dans la colonne *Jury* du PDF précisent le contexte (ex. *Pas de Github*, *Absence de suivi*, *Découverte du travail aujourd'hui*).

## Ce qui nous a été reproché — présentation et fil conducteur

Ce que nous avons entendu sur la **forme de l’exposé** et le **message** (retours oraux) :

- **Pas de fil conducteur** clair : l’audience n’a pas senti une narration qui **mène vers une conclusion** (idée d’un parcours qui se **resserre**, type « entonnoir », jusqu’à ce qu’on comprenne où on veut en arriver).  
- **La gestion de projet** est apparue **tard** dans la présentation — elle aurait dû être visible **plus tôt** dans le déroulé.  
- **Trop de technique**, **pas assez vulgarisée** : difficulté pour les personnes non techniques de suivre ; il manquait une **introduction** et une **mise en contexte** (le **cadre du projet**, l’**entreprise**, le **pourquoi** du sujet). Il y avait pourtant de la matière à présenter — par exemple le travail déjà réalisé par **l’ancien groupe d’étudiants** sur le **calcul du score de criticité**, qu’on n’a pas assez mis en avant.  
- **Où en est le projet ?** L’image donnée, c’était surtout « on est contents de l’avancement », mais **sans éléments concrets** pour que l’audience s’en convaincre elle‑même ; il manquait aussi une **description des critères de réussite** (comment on sait si on a réussi ou non).

## À garder en tête pour la suite

- **Structurer les soutenances** comme attendu dans la grille mi-parcours : **rétrospective**, **plan d’actions**, **prévision de réussite**, **synthèses** et **fil directeur** — pas seulement la technique.  
- **Introduire tôt** : entreprise, cadre, problème, **critères de réussite** et **preuves d’avancement** vérifiables.  
- **Jalons = livrables testables** (une **page / démo** utilisable), pas uniquement des briques parallèles.  
- **Transparence client** : GitHub / backlog / démos **réellement exploitables** ; corréler avec **OG3**, **HO2**, **U1**.  
- **Réunions** : ordre du jour, présence, comptes rendus — lien **CO1**, **CO2**.  
- **Amélioration continue** : introduire **rétrospectives** (**CI1**) et un minimum de **cadre d’équipe** (**MG2**) si ce n’est pas fait.  
- **Score de priorité / criticité** : **co‑construire** avec le client les **poids** (chantiers, opérations, **découpage** des longues rues, etc.) — tel que discuté avec **Hugo LAVEZAC**.
